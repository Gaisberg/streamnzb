# StreamNZB Development Skill

Workflow, commands, and conventions for developing, testing, and building
StreamNZB. This file is committed and shared with every contributor; the
human-facing summary is [`CONTRIBUTING.md`](../../../CONTRIBUTING.md).

## Tech Stack Overview

- **Backend**: Go (1.25+) structured into modular packages under `pkg/` and command entrypoints under `cmd/` (`cmd/streamnzb`).
- **Frontend**: React + Vite + Tailwind CSS + Lucide React + Radix UI, located in `frontend/`.
- **Integration**: The Go server embeds/serves static assets from `pkg/server/web/static`, generated by compiling the frontend.
- **Persistence**: SQLite (`streamnzb.db`, default) or Postgres, via `pkg/core/persistence`. Schema lives in `schema.go` as dialect-neutral DDL using type tokens (`{ID}`/`{INT}`/`{REAL}`/`{BLOB}`/`{TEXT}`); changes go through idempotent migrations in `addedColumns`. Stores hold a `*connRef`, which rebinds `?` placeholders per dialect — write portable SQL, never backend-specific SQL, in a store.

## 1. Verification — ONE command

**All verification goes through the build script.** Do not run fmt/vet/tests/lint as separate verification steps — the script runs the entire pipeline and fails fast on the first problem:

```bash
bash build.sh
```

(On Windows without a Bash shell: `build.bat`. Both are equivalent.)

The script performs, in order:
1. `go fmt ./...` — formats all Go code
2. `go vet ./...` — static analysis
3. `go test ./...` — full backend test suite, including `cmd/streamnzb`
4. `npm run lint` (in `frontend/`) — ESLint
5. `npm test` (in `frontend/`) — Vitest
6. `npm run build` — Vite production build → `frontend/dist`
7. Asset refresh — clears `pkg/server/web/static` and copies fresh frontend assets
8. `go build` with version ldflags (short git SHA + `.release-please-manifest.json`) → `streamnzb` / `streamnzb.exe`

A change is only "verified" when `build.sh` completes with `Build Complete!`.
CI (`.github/workflows/ci.yml`) runs the same steps plus `go test -race ./...`,
and a pull request must be green on all of them.

### During iteration (not verification)
Targeted commands are fine while developing — they never replace the build script:
- Single Go test: `go test ./pkg/path/to/pkg -run TestName -v`
- Single frontend test: `npx vitest run src/lib/streams.test.js` (in `frontend/`); `npx vitest` watches
- Frontend hot reload: `npm run dev` (in `frontend/`)
- **Race detector**: `-race` needs cgo. On a machine without a C toolchain, design concurrent code with mutex/atomic discipline and rely on CI; to reproduce a CI race failure locally, run it in a container:
  ```bash
  docker run --rm -v "$PWD:/src" -w /src golang:1.25 sh -c 'rm -f /.dockerenv && mkdir -p pkg/server/web/static && touch pkg/server/web/static/.gitkeep && go test -race ./...'
  ```
  (`GetDataDir()` returns `/app/data` whenever `/.dockerenv` exists, which breaks the data-dir tests — hence the `rm`.)

### Verification stops at the build script
Do not start the server, the Vite dev server, or a browser to "check" a change unless the user asks. Describe what to look for and let them run it. For playback/streaming work the place to look is `streamnzb.log` (rotated `streamnzb-*.log` files are gitignored).

## 2. Backend Notes (Go)

- Go (1.25+), modular packages under `pkg/`, entrypoint `cmd/streamnzb`.
- Match surrounding style and comment density when editing.

### Architecture — where code belongs

Packages are layered. **Imports only ever point downward in this list.** If a
change seems to need an upward import, the logic is in the wrong layer.

```
cmd/streamnzb              composition root: flags, config load, wiring, ListenAndServe
  ↓
pkg/server/{stremio,api,jellyfin,newznab,web}   HTTP only — parse request, call a service, format response
  ↓
pkg/playback  pkg/search  pkg/search/query  pkg/session  pkg/auth       orchestration + domain logic
  ↓
pkg/media/{unpack,loader,nzb,seek,ffprobe}   pkg/indexer/*   pkg/services/*
  ↓
pkg/usenet/{pool,nntp,speedtest,validation}     pkg/core/{config,persistence,logger,paths,env,metrics}     pkg/release
```

**Where new logic goes** (the handler layer is *not* the default):

| If you are adding… | It belongs in |
|---|---|
| Opening/probing/validating a playback stream, failover mechanics | `pkg/playback` |
| Turning metadata + season/episode into query strings or validation profiles | `pkg/search/query` (pure, no clients) |
| Running searches, validating results | `pkg/search` |
| Session lifecycle, eviction, playback stream leases | `pkg/session` |
| Talking to an indexer | `pkg/indexer/<backend>`, on top of `indexer.ClientCore` |
| Talking to a metadata provider | `pkg/services/metadata/<provider>` |
| Archive plans, stream mapping | `pkg/media/unpack` |
| Segment fetching, read-ahead, zero-fill policy | `pkg/media/loader` |
| Benchmarking a provider (latency, throughput ramp) | `pkg/usenet/speedtest` |
| HTTP request parsing, auth, response shaping | `pkg/server/*` |
| A new client-facing protocol (Stremio, Jellyfin, Newznab, …) | its own `pkg/server/<protocol>` package translating to the same services |

Handlers should read as: resolve inputs → call one service → format the result.
A handler that downloads, STATs, decodes or retries is doing another layer's job.

**Boundaries that are deliberate — do not re-cross them:**

- `pkg/media/loader` must NOT import `pkg/media/unpack`. The segment layer owns
  fetch policy (`fetchpolicy.go`: `ErrTooManyZeroFills`, `PlaybackReadAheadSegments`,
  `WithSkipGapProbing`); the archive layer depends on it, never the reverse.
- `pkg/media/unpack` reaches loader files only through the `UnpackableFile`
  interface it defines, plus optional capability interfaces discovered by type
  assertion.
- `pkg/search/query` is pure: metadata in, strings out. No HTTP, no clients, no
  server state. Anything needing a network call belongs a layer up.
- Only `pkg/usenet/pool` is used for playback segment fetching. `nntp.ClientPool`
  is used directly *only* by the NNTP proxy, the validation checker, and the
  speed tester (`pkg/usenet/speedtest`) — a benchmark must bypass caching,
  singleflight dedupe, provider racing and 430 cooloff, or it measures those
  instead of the provider.

**Key abstractions:**

- `indexer.Indexer` — `Search(ctx, req)` / `Ping(ctx)` / `DownloadNZB` / `Name` /
  `GetUsage`. Composed as client → `CachedIndexer` → `Aggregator`. Shared
  per-client bookkeeping (limits, usage persistence, rate limiter, timing) lives
  in `indexer.ClientCore` — embed it, never re-implement it.
- `unpack.Blueprint` — the cached plan for reaching media inside a release
  (`TargetEpisode`/`Open`/`Kind`), implemented by the rar, 7z, direct and failed
  blueprints. Never pass a blueprint as `interface{}`.
- `nntp.IsArticleNotFound(err)` — the one way to detect a 430. Never match on
  the string `"430"`.
- `playback.Service` — the server drives it via narrow callbacks (config access,
  library persistence) so config hot-reload and once-guards stay in the server.

**Concurrency conventions:**

- Lock ordering is always `Manager.mu` → `Session.mu`. Never invert.
- Never hold a lock across IO. Detach the resource under the lock, act outside
  (see `Session.closeWithLogging`, `acquirePlaybackStream`).
- `Session` state is private; read it through the locked accessors (`NZB()`,
  `Files()`, `Blueprint()`, `Release()`) and **snapshot into a local** before
  dereferencing — never re-fetch after a nil check.
- State shared between a parent and its derived views needs its own lock inside
  the shared struct, not the owner's lock (see `articleStatsRegistry` and
  `leaseRegistry`, both shared by `pool.Pool` and every `Subset`). `Subset()` is
  rebuilt per request, so per-stream state stored in the subset itself would
  reset constantly — it belongs in a registry keyed by lease.
- Never return a pooled NNTP client while goroutines still hold commands on it;
  drain first, or `discard()` instead of `release()`.

### ffprobe Embedding
- Release builds embed a per-platform ffprobe via the `embedffprobe` build tag: `go build -tags embedffprobe ./cmd/streamnzb`.
- Binaries are fetched into `pkg/media/ffprobe/bin/` with `go run ./tools/fetch-ffprobe` (gitignored; never commit them).
- Local/dev builds compile WITHOUT the tag and fall back to ffprobe on PATH or the runtime auto-downloader.
- CI (`.github/workflows/build-release.yml`) fetches ffprobe binaries and builds all platforms with `-tags embedffprobe`.

## 3. Frontend Notes (React)

- React + Vite + Tailwind + Lucide + Radix, in `frontend/`; `npm install` only (`package-lock.json`, no pnpm).

## 4. DRY — Reuse Before Writing

AI-generated code trends toward writing new code instead of finding existing code. Actively counter this:

1. **Search before writing.** Before adding any helper, component, hook, or utility, grep the codebase for an existing one (`formatBytes`, `formatDate`, badge/tile/status components, error helpers, ...). Same rule for Go: check the package and its siblings for an existing function before adding one.
2. **Near-duplicate = extract, don't copy.** If the thing you need is 90% of something that exists, extract the existing one to a shared location (`frontend/src/components/ui/`, `frontend/src/lib/`, a shared Go package) and parameterize the difference — do not paste a tweaked copy into your file.
3. **Prefer editing over adding.** Extending an existing function/component with an option is better than a parallel variant. New files and new abstractions need to justify themselves.
4. **One source of truth per concept.** Formatting (sizes, dates), status→color mapping, API fetch patterns, empty/loading states: each should exist exactly once. If you find two copies while working, consolidate them as part of the change (or flag it if out of scope).
5. **Deleting duplication is a valid deliverable.** A diff that ends net-negative in lines is often the best version of the change.

### Shared helpers that already exist — use them, don't re-inline

A dedupe pass established these. Reaching for the raw pattern again re-creates
duplication that was deliberately removed:

| Need | Use |
|---|---|
| JSON response (api) | `writeJSON(w, status, v)` / `writeJSONError` — never set Content-Type by hand; it must precede `WriteHeader` |
| Admin / method gate (api) | `s.requireAdmin(w, r, msg, methods...)`, `requireMethod`, and `s.adminUsername()` which takes the read lock |
| Add a DB column | append to `addedColumns` in `persistence/schema.go` using a type token; dependent indexes go in `migratedIndexes` |
| Run persistence tests on Postgres | `STREAMNZB_TEST_POSTGRES_DSN=postgres://... go test ./pkg/core/persistence/` (skips to SQLite when unset) |
| Transaction (persistence) | `m.withTx(db, fn)` |
| Delete metric rows | `m.deleteMetricRows(table, nameCol, name, from, to)` |
| A TMDB endpoint | `getJSON[T](c, endpoint, params, label)` |
| An AvailNZB endpoint | `c.doJSON(ctx, requestOptions{...})`; `logAttrs` preserves per-call log context |
| A new env override | one entry in `envFieldCopiers` (config) plus one `r.str` / `r.intVal` call (env) |
| Indexer usage, limits, rate limiting | embed `indexer.ClientCore` |
| Mutate a session under lock | `m.withSession(id, fn)`; host sets via `addHostsLocked` / `sortedHostSet` |
| Mutate a stream and persist | `dm.mutate(username, what, fn)`; convert via `streamFromEntry` / `streamToEntry` |
| Proxy article command | `s.forEachProvider(verb, msgID, attempt)` |
| Log a stream name | `streamLogName(stream)` |
| Log a search mode | `indexer.SearchModeLabel(mode)` |
| First non-empty string | `firstNonEmpty(...)` (cmd) |
| Clear a `sync.Map` | `clearSyncMap(&m)` |

Two notes on finding dead code: `staticcheck -checks U1000` reports unused
*unexported* code but **cannot see unused exported code**, so verify exported
helpers by reference count. And deletion cascades — re-run it after each removal
until it comes back clean.

## 5. Development Workflow Checklist

When implementing features or bug fixes:

1. Write/update backend and/or frontend code (match existing style; reuse per §4; add tests for new behavior — a bug fix should include a test that failed before the fix).
2. **Verify with the build script**: `bash build.sh` (or `build.bat`) — fmt, vet, all tests, lint, frontend build, and binary compile in one shot.
3. **Update documentation** when the change is user-facing (per §7): edit or create the relevant page under `docs/`, not the README.
4. **Check the staged list** for build artifacts (per §6) before committing.
5. **Propose a Conventional Commit message** (per §6) — the same text becomes the pull request title.

## 6. Commit & Pull Request Conventions

- **Conventional Commits** are mandatory — release-please derives versions and changelogs from them. Pull requests are squash-merged and the PR title becomes the commit subject, so the title must be a valid Conventional Commit too.
  - Types in use: `feat:`, `fix:`, `perf:`, `refactor:`, `docs:`, `test:`, `ci:`, `chore:`; optional scope like `feat(stremio):`, `fix(loader):`; `!` after the type/scope for a breaking change.
  - Describe the behavior change, not the code change: `fix(loader): scope the segment size estimator to one release`, not `fix: update loader.go`.
- **One change per pull request.** A small enabling refactor may ride along if mentioned; an unrelated fix may not.
- **Never add attribution trailers** (`Co-Authored-By`, `Generated-by`, etc.) to commit messages.
- **Never commit build artifacts**: `streamnzb`, `streamnzb.exe`, `pkg/media/ffprobe/bin/*` binaries, `/ffprobe`, `*.log`, `streamnzb.db*`, `config.json`, `frontend/dist/`, `pkg/server/web/static` (all gitignored — verify staged lists stay clean on large commits).
- **Dependency bumps** come from Dependabot (`.github/dependabot.yml`), grouped per ecosystem. Don't hand-roll them.

## 7. Documentation — reference lives in `docs/`, not the README

User-facing documentation is split into two tiers:

- **`README.md`** is the landing page only: pitch, "What it does", quickstart, setup guide, and a **Documentation** link list. Do not append feature reference material to it — that is how it bloated to 235 lines before the split.
- **`docs/`** holds the reference pages, roughly one page per feature/Settings area (`database.md`, `speed-test.md`, `easynews.md`, `metadata.md`, `stream-model.md`, `availnzb.md`, `aiostreams.md`, `jellyfin.md`, `troubleshooting.md`), indexed by `docs/README.md`.

When a change adds or alters user-facing behavior (a setting, env var, feature, or troubleshooting scenario), update the matching `docs/` page in the same diff — or create a new page if none fits. A new page must also be linked from **both** `docs/README.md` and the README's Documentation section, with a one-line description. Deployment-level env-only knobs are documented in their feature's docs page, not the README.

Contributor-facing process lives in `CONTRIBUTING.md`; architecture and conventions live here. Keep the two in sync when either changes.

## 8. Project-Specific Design Principles

- **Client codec responsibility**: never reorder, hide, or gate streams by client User-Agent to work around codec incompatibility (HEVC 10-bit, Dolby Vision, ...). Surface capability metadata client-agnostically; the client/device decoder decides what it can play.
- **Validation is layered**: article existence → STAT sweeps; archive structure → RAR scan/blueprint; real-video/decodability → ffprobe; sustained playability → playback itself with failover as backstop. Use the right layer for the question — don't probe existence with a decoder.
- **Fail-open on inconclusive checks**: only definitive evidence (430 on all providers, corrupt data) may poison a release/slot; transient errors (timeouts, cancellations) must never blacklist anything.
- **Benign-disconnect noise**: intentional teardown errors (`context canceled`, `use of closed network connection`) log at Trace via `nntp.IsBenignDisconnect`; real failures (430, protocol errors) stay at Debug+.
