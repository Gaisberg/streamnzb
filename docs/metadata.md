# Metadata & Catalogs

StreamNZB is a full metadata provider — your client needs no other addon or application for browsing, search, or title pages. Metadata is configured as **profiles**: each profile is a named bundle of catalogs, sources, display language and an optional rating limit, and every stream binds one profile (or none) on the Streams page.

## Profiles

- **A profile per audience** — Create as many profiles as you like on the **Metadata** page: a full catalog board in English for the living room, a capped kids profile in another language for the tablet. Each stream picks its profile on the Streams page, so two installs of the same server can serve completely different boards.
- **Binding is the enablement** — A stream with **no** metadata profile bound serves streams only: the manifest is byte-identical to the pre-metadata addon, and clients keep using Cinemeta or whatever they already have. There is no separate on/off switch anymore.
- **Migration** — Upgrading from the single global metadata config seeds a **Default** profile from the old settings and binds it to every existing stream, so nothing changes until you say so. If the old master switch was off, the profile is created but left unbound.
- **Renames follow, deletes clear** — Renaming a profile updates every stream bound to it; deleting one unbinds its streams, which fall back to the stream-only manifest.
- `METADATA_ENABLED=false` (env) remains a deployment-level kill-switch that blanks metadata for every stream regardless of bindings.

## What a profile carries

- **Catalogs** — A fresh profile serves one trending row per media type (movies, series, anime). The registry offers 36 catalogs across TMDB, TVDB, Kitsu, Simkl and local rows (popular, top rated, now playing, upcoming, Popular/New on TVDB, Simkl watchlists, and more): add them from the search dialog, drag to reorder, remove with one click. A title appears only in the highest-ordered catalog that carries it; the row order doubles as the dedup priority.
- **Insufficient metadata** — *Hide content with insufficient metadata*, under the catalog list, is on by default and drops rows no source could describe: the ones that arrive with no artwork at all, which every client renders as a blank tile. In practice these are duplicate records, placeholders and announcements a provider has never filled in. It is checked only after every source in the type's priority list has had its turn (and after the gaps have been filled from the sources behind the leader), so a row is dropped only when nothing you ranked could describe it. Catalog sources you pasted yourself are exempt — a list you chose stays complete.
- **Unreleased content** — *Show unreleased content up to X days out*, under the catalog list, sets how far ahead a scheduled title may be and still appear in catalog rows and search results. The default is 30 days: what is about to land shows up, announcements years out do not. A title a source explicitly calls *upcoming* without publishing a date is hidden too — nothing can place it inside a window — while one that simply has no date and no such status is always shown, because that is missing data rather than a distant release. Rows the catalogue sources could not date are dated from **TVMaze** when the profile has *TVMaze air dates* on (the default), which is also where the "not out yet" statement comes from for sources that publish no status: a record TVMaze lists as *In Development* or *To Be Determined* with no premiere date counts as unplaceable. Switch that toggle off and the window falls back to whatever dates the catalogue sources themselves publish. Zero shows only what has been released; the far end of the slider hides nothing upcoming. A title whose source publishes no date at all is always shown — that is missing data, not a distant release — so an empty upcoming record with no date on it still appears.
- **Search** — Always available for every content type, independent of the catalog rows a profile picks. Each type is searched at **the source it ranks first** (see *Sources* below), with the rest of its list as fallbacks when the leader has no answer. The manifest carries hidden search-only catalogs (their search extra is declared *required*, so clients use them for search but never render them as board rows) — a kids profile built purely from family rows still searches all three types, and search results respect the profile's rating limit like everything else. A title two carriers both know — an anime that TMDB also lists as an ordinary series — comes back once, from whichever source the media type's priority list ranks highest. The anime list names only Kitsu and TVDB, so an anime is answered by the leading anime source and the series carrier's copy of it is dropped; with Kitsu leading that means one result per cour, the way Kitsu splits the series, and with TVDB leading one result for the whole series.
- **Family & kids catalogs** — **Family Movies**, **Animated Movies**, **Family Series**, **Kids TV** and **Kids Anime** are filtered at the source (TMDB Discover by genre and US certification, Kitsu by age rating), so they return full pages of actually kid-targeted content instead of general rows thinned out by a cap. They are the intended building blocks for a kids profile: Family Movies carries a built-in PG ceiling and Kids Anime a G/PG one even on uncapped profiles, and a profile's rating limit tightens the source filter further (an All-ages cap turns Family Movies into `certification.lte=G` and Kids Anime into G-only). The general rows (trending, popular, …) can't be pre-filtered upstream, so under a cap they only show whatever happens to pass — expect them to run short on strict caps.
- **Sources** — Each media type has its own **priority list** of metadata sources under *Sources & language*: drag to reorder, and the first source that can serve a title is the one used, with the rest tried in order behind it. The list governs **search as well as title pages**: with the default series order a series search is answered by TVDB, and a record TVDB has but TMDB has never populated shows up as a real row instead of a blank card. Rows a leading source leaves thin are completed from the next source in the list — TVDB publishes no rating, so its rows pick one up from TMDB — but never overwritten: what the leading source published is what the profile asked for. Movies choose among TMDB and Cinemeta, series among TVDB, TMDB and Cinemeta, anime among Kitsu and TVDB. The defaults are what StreamNZB has always done — TMDB for movies, TVDB then TMDB for series, Kitsu then TVDB for anime — and TVMaze remains the air-date authority throughout. Two things worth knowing: **Cinemeta is opt-in**, appearing in no default list, and it carries no age-rating data, so a title served from it stays hidden under a rating limit unless *Allow unrated content* is on; and **anime always keeps Kitsu's playback IDs**, so reordering anime sources changes only the artwork and text, never episode matching or stream lookup. The per-profile TVMaze toggle governs the air dates shown on title pages *and* the dates the unreleased-content window filters by; skipping unaired episodes is a per-stream indexer setting (**Streams → pick the stream → Indexers → Skip unaired episodes**) and always uses the best air date it can find, for every stream, whether or not it binds a metadata profile.
- **Language** — Titles, overviews, episode names, logos and catalog rows display in the profile's language. TMDB content localizes fully; TVDB series and episodes overlay TheTVDB's translation for the profile's language, English included — TheTVDB's own record is the show's original language, so English is requested like any other; anime keeps its Kitsu titles and English synopsis, and picks up a translated description through the anime-lists mapping for other languages. Anything without a translation keeps TheTVDB's default record. Different streams can run different languages side by side. Clients cache title pages for a few hours, so a language change reaches already-visited titles after their cache expires. Independent of the language a search request's Title attempts query under, which controls what gets sent to indexers.
- **Poster overlays** — An optional per-profile **Poster overlay URL** replaces posters with an overlay service's artwork: ratings, quality badges (4K, Dolby Vision), genre and age-rating tags baked into the image. It is a URL template containing `{imdb_id}` — [BetterPosters](https://btttr.cc/configure) (free, no key; pick *AIOMetadata / Other Addon* to generate the URL with your tag and language choices) and RatingPosterDB both emit one. Clients fetch the posters directly from the service, so nothing extra flows through your server. Overlay services key on IMDb ids: anime resolves to its series-level IMDb id through the anime-lists mapping, which means every season/cour of a show shares one overlay poster instead of Kitsu's per-season art. The occasional row that only resolves to a TMDB/TVDB id — and anime too new for the mapping — keeps its original artwork, and so does a title the service has no poster for: the overlay URL is checked once per title (cached for a day) and skipped when it answers 404, rather than substituted blind and rendered as a blank tile. Title pages and catalog rows are client-cached, so a change appears as those caches expire.
- **Rating limit (parental controls)** — Cap the profile at an age certification (All ages / 7+ / 13+ / 16+ / 18+). The cap applies everywhere: capped titles disappear from catalog rows and search, their title pages 404, and playback requests return no streams. Certifications come from TMDB (movies and series), TVDB (series) and Kitsu (anime), preferring the US rating and falling back to the strictest known foreign one.
  - **Unrated content is blocked by default.** Certification data is patchy — niche and foreign titles often have none — and a parental control must fail closed. The per-profile **Allow unrated content** toggle opens that up if the limit proves too aggressive.
  - **"Metadata off" is not kid-safe.** A stream with no profile bound has no cap at all — a kids device needs a capped profile *bound to its stream*.
  - Search caches are cleared when profiles or bindings change, so a tightened cap takes effect immediately on playback; clients may still show cached catalog rows and title pages for up to their cache lifetime.

## Simkl

Link a [Simkl](https://simkl.com) account from the **Simkl** card in a stream's settings (**Streams → pick the stream**) and that account's watchlists become catalog rows for that stream: **Watching**, **Plan to Watch**, **On Hold**, **Completed** and **Dropped** for series and anime, and **Plan to Watch**, **Completed** and **Dropped** for movies (Simkl has no watching/hold state for movies).

- **Linking** — Pick the stream on the Streams page, click **Connect** on its Simkl card, enter the shown code at [simkl.com/pin](https://simkl.com/pin/) and approve the app; the page updates by itself once Simkl confirms. The rows then appear in the *Add catalog* dialog — they are opt-in per profile like any other catalog. Disconnecting hides the rows again but keeps the toggles, so a re-link restores the same board.
- **One account per stream** — The link belongs to the stream, not the server: everyone with their own stream links their own Simkl, and a profile shared by several streams serves each of them their own watchlist through the same row. Rows appear in the *Add catalog* dialog as soon as any stream has linked an account; a stream that has linked none serves them empty.
- **Freshness** — The watchlist is cached and revalidated against Simkl's change feed about once a minute (Simkl's API terms require clients to avoid refetching unchanged lists), so an addition on Simkl reaches the board within a minute or two. The rows themselves are marked never-cache toward clients, like Continue Watching.
- **Anime** — Simkl keys anime by MyAnimeList id; StreamNZB resolves it through the anime-lists mapping onto the same Kitsu-based pipeline as the anime catalogs, falling back to the entry's IMDb id when the mapping has no answer yet. An anime with neither is skipped.
- **Scrobbling** — Switched on per stream, not here: see [Scrobbling](#scrobbling) below. Once playback is proven real (the same sustained-play threshold that marks a release good), the title shows as *watching now* on Simkl; when the play stops, the furthest position playback is known to have reached goes out as progress — Simkl marks the title watched past 80% and keeps the resume position below that, so a film abandoned at 44% appears at 44% in Simkl's playback-progress manager. Anime scrobbles only when the MAL mapping knows the entry, and direct NZB plays (no title identity) never scrobble. The same playback can be reported to MDBList at the same time — see [MDBList](#mdblist).
- **Client ID** — Release builds carry a built-in Simkl client id. To use your own Simkl app instead, create one at [simkl.com/settings/developer](https://simkl.com/settings/developer/) and paste its client id under **API keys** (`SIMKL_CLIENT_ID` env also works); changing the id unlinks the current account until it is re-linked.

## MDBList

Playback can also be reported to an [MDBList](https://mdblist.com) account, from the **MDBList** card in the same stream editor, next to the Simkl one. Unlike Simkl it brings no catalog rows with it — public MDBList lists import from their URL with no account at all, see [External catalog sources](#external-catalog-sources) — so the card exists purely for scrobbling.

- **Linking** — Pick the stream on the Streams page, click **Connect** on its MDBList card, enter the shown code at [mdblist.com/oauth/device](https://mdblist.com/oauth/device/) and approve the app; the page updates by itself once MDBList confirms. The link uses MDBList's OAuth device-code flow rather than an API key, so nothing secret is ever pasted into StreamNZB, and the grant can be revoked from your MDBList account at any time.
- **One account per stream** — Like Simkl's, the link belongs to the stream. MDBList brings no catalog rows, so the account is used for nothing but this stream's scrobbling.
- **Token renewal** — MDBList access tokens last 30 days. StreamNZB renews them in the background from the refresh token it was issued, so a linked account keeps working indefinitely; if MDBList ever refuses the renewal (the app was revoked, the account deleted) the card falls back to disconnected and asks for a re-link rather than failing silently.
- **Scrobbling** — Switched on per stream, like Simkl's and independently of it: see [Scrobbling](#scrobbling) below. MDBList marks a title watched past 80% of the progress reported and keeps the position as a resumable playback below that, so it surfaces in its continue-watching alongside anything else writing into the same account.
- **Anime** — MDBList addresses everything by the aired series, so anime is scrobbled as the TVDB/TMDB/IMDb series and aired season/episode that anime-lists resolved the Kitsu entry onto, and an anime film as a movie by its IMDb id (anime-lists prefers an entry's TMDB *series* record, so its TMDB id cannot be trusted to name a film). An entry the mapping only knows a MyAnimeList id for has no MDBList address and is skipped there — it still scrobbles to Simkl, which addresses anime per MAL entry.
- **Client ID** — Release builds carry a built-in MDBList client id. To use your own app instead, register a **Device Code App** at [mdblist.com/developer](https://mdblist.com/developer) — it needs no redirect URI — and paste its client id under **API keys** (`MDBLIST_CLIENT_ID` env also works); changing the id unlinks the current account until it is re-linked.

## Scrobbling

Linking an account (above) only makes it available to that stream. What actually reports playback into it is the **Scrobble playback** switch inside the same card, which appears once the account is connected and is off by default. Linking for catalog rows and reporting your viewing are separate decisions.

- **An account per stream** — Each stream links its own Simkl and MDBList accounts, so everyone in a household reports into their own history. Nothing is shared and nothing is exclusive: two streams scrobbling at once are writing to two different accounts.
- **Not per device** — A stream's addon URL can be installed on as many devices as you like, and all of them report into that stream's account. A living-room TV and a tablet signed in to the same stream both scrobble to the same place, which is usually what you want.
- **What is reported** — Progress is measured from the bytes actually served (probe requests players make against the file are ignored), so no client cooperation is needed — but it is an estimate of position, not of what was on screen. A player buffers far ahead of what it is showing, so served bytes alone would call a film watched the moment it finished downloading; each request is therefore credited only from where it asked to play plus as much as its runtime says could have been played while it stayed open. Seeking forward still moves the position immediately, because that is the player saying where it is. Both services mark a title watched past 80% and keep a resume position below that.
- **Upgrading** — Accounts used to be linked once for the whole server. That link is **cleared on upgrade**, along with the old server-wide *Scrobble playback to Simkl* switch: there is no way to guess which stream a server-wide account belonged to, and guessing wrong would file one person's viewing into another's history. Link again from each stream that needs one, then turn its *Scrobble playback* switch on. Stream settings save as you change them. This happens once — links made afterwards persist normally.

## Personal rows & artwork

- **Personal rows** — **Continue Watching** and **Because You Watched** are built from each stream's *own* playback history, so every household member with their own stream gets personal rows from the same server. Simkl watchlist rows are personal to the linked account — see above.
- **Artwork** — Catalog rows carry landscape backgrounds alongside posters (TMDB backdrops, TVDB fanart, Kitsu covers), so clients that build featured-hero banners from catalog rows render a proper backdrop instead of an upscaled poster. Backgrounds on title pages pick the community's highest-ranked fanart, title logos come from the source itself (TVDB clearlogo, TMDB logo) with Cinemeta's logo CDN as the fallback, and cast lists carry actor photos. Anime title pages upgrade their background and logo through the anime-lists mapping to the matching TVDB/TMDB record, keeping Kitsu's posters.

## External catalog sources

Browse rows can come from somewhere else: a public Stremio addon manifest, or a public TMDB, MDBList or Letterboxd list. **Paste the URL straight into the search box of the *Add catalog* dialog** — the box searches the built-in catalogs and accepts a source URL, and anything starting with `http://` or `https://` is treated as a source. Press **Check source**, and StreamNZB fetches it once and offers the rows it could actually read; pick the ones you want. A source already on the profile says so before you check it, and rows you already have are marked. Imported rows behave like any other catalog — reorder them, rename them, remove them — except that they are never deduplicated against the rows above them, so a list you chose stays complete.

A pasted row serves its whole list, not just its first page. A source that declares paging is asked for each page; one that hands its entire list over in a single response is paged locally. Both spellings of the manifest's paging contract are read (`extra` and the older `extraSupported`), so a row is not capped at 20 items because its addon uses the older one.

Only catalogs are imported. An external addon's search, streams, subtitles and configuration are never used, no credentials are ever sent, and the artwork and titles shown come from your own metadata sources rather than the pasted source.

### Self-hosted catalog sources

Fetching a pasted URL refuses to connect to a private, loopback or link-local address. That is deliberate: without it, anyone who can add a catalog source could use the server as a probe of the network it runs on. It also means a Stremio addon on your own LAN is unreachable until you say which networks are yours.

List them in `catalog_source_networks` in `config.json`, or set `CATALOG_SOURCE_NETWORKS`:

```json
{
  "catalog_source_networks": ["192.168.1.0/24", "10.0.0.7"]
}
```

Entries are CIDRs or single addresses, exactly like `trusted_proxies`. A catch-all such as `0.0.0.0/0` is rejected rather than quietly turning the check off. The setting is intentionally config/env only and is not shown in the dashboard, so a compromised dashboard session cannot widen it.

The manifest URL itself must still be `https://`, so a self-hosted addon needs TLS — a reverse proxy with a certificate for an internal hostname is the usual way. If a source that should be reachable still is not, the source test says which address it refused.

> **Note:** an outbound HTTP proxy (`HTTPS_PROXY`) is not used for these fetches. Every connection has to be checked against the address it actually reaches, which is impossible when it is handed to a proxy instead.

## API keys

The TMDB and TVDB keys, and the Simkl and MDBList client ids, are shared by every profile and live in their own section at the bottom of the Metadata page. Built-in fallback keys make this work with zero setup; adding your own raises the ceiling and is recommended for anything beyond personal use.

A key is verified against its provider as you leave the field and is only stored once the provider answers — if it is rejected, the reason appears under the field and nothing is saved. Two things trip that up:

- **TMDB** wants the long **Read Access Token** from its API settings page, not the short v3 API key.
- **TVDB** only accepts a key that authenticates on its own. A key from TheTVDB's self-service signup is tied to an individual subscription and is rejected here with a 401 — leave the field blank and use the built-in key instead, which carries no quota you would need to escape.

Saved keys are never shown back, so the fields start blank on every visit; leaving one blank keeps whatever is already stored.

> This product uses the TMDB API but is not endorsed or certified by TMDB. Series metadata is provided by [TheTVDB](https://thetvdb.com) — consider subscribing to support them.
